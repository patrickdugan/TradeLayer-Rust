# zkTL-Bridge protocol sketch v0 (ZTB-01)

## Scope and trust boundary

NEAR holds a separately accounted reserve of one pinned NEP-141 token. Bitcoin provides the canonical ordered inputs to a new, explicitly activated TradeLayer economic domain. A TL stablecoin claim is transferable either as a ledger atom balance or a token-bearing Bitcoin outpoint. Trading and clearing redistribute claims against the same reserve. No NEAR operator key may authorize an arbitrary mint or withdrawal. Token issuer freeze/blacklist, contract upgrades, chain finality, availability and circuit soundness remain explicit assumptions. Pilot uses mock USDC and regtest/testnet, never live funds.

Existing code seams: [type 36](../../src/zk_verify.rs), [registry](../../src/registry_zk.rs), [economic owner](../../src/economic_zk_impl.rs), [Nova verifier](../../docs/ZK_VERIFIER_NOVA.md), [deposit attestation](../../docs/ZK_DEPOSIT_PROOFS.md), [commitments](../../docs/PROVING_COMMITMENTS.md), [settlement authorization](../../docs/SETTLEMENT_AUTHORIZATION.md), [contract economics](../../docs/ECONOMIC_CONTRACTS.md). Type 36 currently supports statement receipts only. Legacy raw 33/34 are incomplete; see [source tail](../../docs/SOURCE_TAIL_LIFECYCLE.md). Do not silently activate or reinterpret them. TLPT snapshot digests are audit metadata; introduce a separately versioned authenticated state synchronized with the actual economic owner.

## Accounting

Each asset domain pins both network identities, NEAR token + vault account, TL property ID, activation anchor, policy, program and verifier identities. Use checked integer atoms (USDC six decimals; explicit conversion to TL ledger precision), range constrain all counters and arithmetic before field reduction.

D = confirmed retained deposits, M = minted, B = burned, R = successfully paid. U = live UTXO-bound atoms, A = available ledger atoms, C = all reserved ledger atoms (spot, margin, channels, fees and insurance counted once). O = U+A+C = M-B, Q = B-R. D >= M >= B >= R. D-R >= O+Q; the actual economically spendable vault reserve must cover all liabilities including in-flight payout state. Unminted balance D-M remains dedicated to depositors. Vault loss, token freeze, unexpected balance changes and post-payout reorgs trigger a halt and recovery policy. A refund protocol would need mutually exclusive deposit consumption/refund proofs; v0 disables refunds.

Model is deliberately smaller: one asset, available and margin maps plus live and spent outpoints; it omits spot, fee, insurance, source authentication and active position risk. Releases in the model presume external closeout authorization. Never call the model to authorize money.

## Transitions

Deposit: verify exact retained amount after successful NEP-141 resolution; append unique deposit record bound to target BTC recipient, property and domain. Account for asynchronous receipt resolution: pin the token predecessor, deposit id, actual retained amount, and prove terminal successful execution (or authenticate final vault state with a proved invariant that no deposit can be refunded after inclusion). No event log alone suffices.

Mint: consume one authenticated deposit nullifier, credit its pinned recipient once; a proof receipt alone has no custody effect. Export/import and UTXO transfer atomically move atoms between representations. Every spend of a token-bearing outpoint must have a deterministic transition, including unrecognized/non-protocol spends (specify burn or recovery semantics before activation); no unaccounted resurrection. Authenticate spend and output identity on the canonical Bitcoin chain. For proof submitters distinct from recipients, bind both explicitly using the type-36 sender/expiry prefix; a copied proof may never redirect issuance.

Reserve/release: the existing economic owner moves atoms to/from actual escrow accounts with order/margin authorization. PnL: a witness graph f_ij >= 0 matches authenticated net obligations delta_i = sum_j f_ji - sum_j f_ij, with sum_j f_ij <= eligible collateral_i under a pinned policy. Prove signatures, price, contract semantics, rounding, bankruptcy/insurance and absence of prior settlement; conservation alone cannot authorize payment. Prefer linear USDC margined contracts first. Payout claims derive only from free post-risk available balance.

Burn: debit available balance atomically, append unique withdrawal leaf binding destination NEAR account, amount and originating event. Pending -> InFlight(attempt) -> Paid, or Pending on verified failed transfer. InFlight consumes a reservation; retries are allowed only following authenticated failure of the exact attempt. Only a private callback from the vault's own promise may mark success, with exact attempt binding. A successful external transfer whose callback fails requires recovery/reconciliation without resending. R updates only upon successful transfer confirmation; reserve checks include outgoing obligations already in flight. Test stale callbacks, failed callback after successful payment, storage exhaustion and concurrent attempts. No automatic timeout-based retry of ambiguous outcomes.

## Proof programs

| Program | Relation | Receiver |
|---|---|---|
| NEARHEAD01 | Pinned genesis/checkpoint, NEAR light-client approval signatures, stake thresholds and validator epoch transitions, authenticated execution/state roots | TL Nova Pallas/Vesta profile |
| NEARPAY01 | Deposit membership or execution proof against authenticated NEAR root; exact contract, token, amount, destination and nullifier | TL type 36 and new custody effect |
| TLSTATE01 | Complete ordered authorized economic execution from previously accepted state, including hybrid outpoints, supply, trade/mark/settlement/withdrawal effects | NEAR transparent decider |
| TLEXIT01 | Claim membership, exact Bitcoin checkpoint and canonical chain policy, with TLSTATE01 acceptance | NEAR vault |

NEARHEAD and NEARPAY may be composed in one pinned circuit or independently verified receipts with exact shared root binding. NEAR light-client protocol and its signature/cost envelope require fresh specification and test vectors; a signed relay claim is not a finality proof.

TLSTATE01 state commitment namespaces: balances, token outpoints, spent outpoints, order queues/reserves, positions/margin, oracle policy/history, deposit consumption, exits, fees/insurance and global replay markers. Include chain tip, height, asset domain, transition count and previous root. Domain-separate all trees and leaves. Use circuit-friendly incremental commitments with a native Rust differential oracle. Authenticate every relevant ordered Bitcoin input, including prevouts and witness commitment where authority depends on witnesses. Full replay must demonstrate completeness (recompute transaction Merkle root from complete ordered block, handle mutation ambiguity and canonical parsing, authenticate witness root, prevouts and canonical Bitcoin chain); individually included transactions can omit losses. A dedicated bridge lane is a separate protocol with explicit ordering, inclusion/DA and escape rules. Never switch between lanes silently.

## Checkpoint and statement ABI proposal

40 bytes in Bitcoin OP_RETURN: ASCII TLBRDG01 (8) || SHA256(canonical statement) (32). Statement schema to freeze in ZTB-02: version, domain, both chain identities, token/vault and property, previous and next roots, contiguous block range + parent/tip, deposit and withdrawal roots, M/B, policy/program/key hashes. Use explicit bounded lengths, endian conventions and exact domain tags; digest splits to two constrained u128 limbs, never reduction modulo a field. Anchoring transaction is outside the range it commits to, avoiding self-reference. NEAR must verify both exact Bitcoin inclusion and TL validity; an OP_RETURN is not authorization. Canonical chain selection needs ongoing competitive chainwork and a confirmation policy; SPV proves inclusion under assumptions, not global heaviest-chain knowledge. Pre-finality reorg revokes eligibility. Post-payment deep reorg requires emergency accounting and reserve policy.

Only advance from the previously accepted root, with monotone finalized interval. Multiple concurrent proof sessions may run, but compare-and-swap the expected predecessor at finalization. Bind all chunks to pinned VK, proof digest, public input and session; enforce exact chunk coverage, no duplicates and atomic finalization. Withdrawal leaves and paths must be publicly available and reconstructible without an operator.

## Existing proof paths and cost

- [TL Nova profile](../../docs/ZK_VERIFIER_NOVA.md): Pallas/Vesta ppsnark IPA, compact 553-byte registered key; NHC1 12,784 bytes, cached native verify 1.81 s. Type 36 node frame cap 30,000 bytes and block budget 4,000 ms per source; benchmark proposed new programs before activation. Custody movement requires Phase 2. No trusted setup.
- [M12-M18](https://github.com/patrickdugan/zk-rusto-no-bitcoino/tree/main/integrations/bitvm3-nova): M16 mainnet header chain + payment proof, M18 windowed UTXO commitments, M12/13 Nova verifier inside SP1 and BLAKE3 wrap, M14 garbled verifier. M16 payment inclusion is not a proof of TL economics; M18 window requires an authenticated starting state. BitVM3 enforcement is a future Bitcoin custody path, not required to release NEAR escrow.
- [INDEX-03](https://github.com/patrickdugan/SatsHedgeZero/blob/research/shz-hourly-index-nova-03-20261124/docs/SHZ_INDEX03_TRANSPARENT_NEAR_VERIFIER.md): distinct bounded single-curve BN254 NIFS + Spartan/IPA decider, not the Pallas/Vesta two-curve compressed SNARK. [Sandbox receipt](https://github.com/patrickdugan/SatsHedgeZero/blob/research/shz-hourly-index-nova-03-20261124/research/hourly_index_nova_03/artifacts/near_sandbox_receipt.json) reports 10,003-byte proof, 1,129 txs, 196,381 TGas total, 8/8 adversarial controls. Use as reference subject to soundness audit, especially exact fold and final relation. No production authorization implied. Test transparent succinct wrapper (M13-style or alternative) against actual proof bytes and exact program/public input binding; verify on NEAR directly, not via BitVM garbling. Groth16 option only with explicit accepted ceremony policy, never a hash-of-proof substitute. Respect license boundaries when importing code; GPL tools may run out of process.
- [SatsHedge three-party clearing](https://github.com/patrickdugan/SatsHedgeZero/blob/main/docs/TESTNET4_3PARTY_NOVA_CLEARING.md): 3 folds, 12,376-byte proof; native and Nova verification reported, on-chain BitVM3 verification false. Reuse the typed transcript/settlement binding concepts, not claims of economic authorization unsupported by the constraints.

Production gates: reviewed native and circuit equivalence, cryptographic authentication in both directions, exact finality and replay policy, successful adversarial contract sandbox, measured cost and liveness, immutable or delayed/limited governance, independent audit, bounded testnet pilot. Until then production_ready=false, can_mint=false, can_redeem=false.

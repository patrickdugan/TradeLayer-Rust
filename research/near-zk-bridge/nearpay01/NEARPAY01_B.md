- [FunctionCallAction](https://github.com/near/nearcore/blob/440567f0a21df411a54b28fef2ebe586920b599d/core/primitives/src/action/mod.rs): tag 2, Borsh method string, args vector, gas u64, deposit u128. Transfer tag 3, deposit u128. Other actions refused.

The reference opens the WHOLE destination receipt list (cap 256 receipts, 256 KiB, 8 KiB args) with a cursor that rejects truncation, trailing data, unknown versions/actions, noncanonical option tags, invalid account IDs and duplicate IDs. It selects the expected receipt ID at a specified index. Lists with unsupported unrelated receipts fail closed; a production decoder needs full supported version coverage or a separately sound streaming parser. Header root is not passed separately from the authenticated bytes. Block ancestry folds against a pre-pinned synthetic head root as in A; real finality and shard-layout authentication remain required.

## Data dependency

Given independently authenticated receipt lists and outcomes, decode exact receiver and resolver FunctionCall actions and data receipt. Require the receiver output data ID and resolver input data ID to match, the destination token to be the same, and the DataReceipt predecessor/receiver to be vault/token. DataReceipt.data must be Some(exact receiver SuccessValue bytes). Verify one call per receiver/resolver, proper predecessor and executor, identity agreement, and distinct receipt IDs. Return authenticated-argument *candidates*; A's argument semantics and canonical logs must be bound to parsed bytes in the final composed circuit. The synthetic fixture deliberately uses only the topology, not complete authentic chain scheduling or an actual token implementation. No caller-provided verified boolean is accepted.

NEAR may execute local receipts without the outgoing-list proof route, especially the initial signed transaction and same-shard resolver. Some generated receipts can be buffered across chunks. Outgoing commitment is to previous chunk execution, not necessarily the execution at the commitment block's height. Do not assume same height, universal receipt-list availability, or that an outcome's child IDs alone prove the receipt body. For same-shard/local cases, authenticate the signed transaction through chunk tx_root and/or a state-trie receipt proof or a pinned-code execution relation; must account for actual nearcore receipt creation and data delivery. The current implementation only covers receipts actually present in authenticated outgoing lists. Need real chain vectors, cross-shard generation/execution ordering, authenticated epoch shard layout (including reshards), code identity and complete A+B composition before enabling a credit.

## Nova circuit plan

Whole-list SHA-256 is linear in list bytes, no per-receipt path exists within ReceiptList. Stream 64-byte SHA blocks using fixed step shape, carrying chain state, exact byte length, cursor/receipt index and a rolling commitment to parsed fields; enforce canonical padding and total consumption. For the selected receipt, constrain parser and byte-to-field mapping, not a detached host-provided parse. Authenticate the header and Merkle paths through typed folds; branch direction and odd-width omission are derived from authenticated layout. Domain and finality head are fixed across folds, connect A outcome IDs and data bytes to B outputs, and consume both A nullifiers atomically only after full proof verification.

A 256 KiB list has 4,097 SHA-256 compression blocks including padding (worst case at exact cap); a 4 KiB list has 65. Benchmark small actual lists first; keep prover workload and type-36 verifier dimension bounded. Consider a full-retain deposit profile with a unique authenticated vault finalization event and pinned token code to avoid expensive generic graph witnesses only if a separate soundness review proves it sufficient. Never replace action authentication with an arbitrary RPC response hash.

# Guarded generation escrow and read-only ACK history

An explicit ESCROW-WAL service mode now binds generation-retention policy in its immutable origin/context. For a native append that will cross a publication boundary, the real controller first syncs the raw action Intent, obtains an actual sealed generation copy/permit, then syncs a second EscrowBoundIntent before guarded native IO. The same rule applies to a replacement native plan. A lost control-write return retains the same permit, source frame and computed financial prefix; recovery retries only the retained write or native plan. It does not rerun source decoding, Logic or the whole action. Ordinary noncompacting appends create no copy.

Independently pinned retained-prefix reads check the full actual copied KV/row stream even when the point was not in the original bounded whitelist. The old whitelist reader retains its admission rule. Original source and actual copied physical paths/identities remain distinct. Corrupt or missing retained evidence refuses before pruning/publication. Existing native/history modes and their origin bytes remain unchanged.

The mode also installs a temporary inline-write guard. Ordinary inline metadata puts that would compact refuse before publication until the retained inline operation PC is integrated. This refusal is a safety boundary, not successful source parity or inline recovery. The default unguarded source put path preserves its original Journal commit call. Inline processBlockData/save-height/startup success, caught rejection and lost-return recovery remain separate work.

The new VerifiedActiveServiceAckHistoryV1 is a read-only real-file reader for the existing HISTORY-WAL mode. It opens an independently expected synced Ack prefix under the actual file lock, follows the complete contiguous hashed entry chain back to immutable origin, verifies every required raw action/Before/Accepted/native/history blob and continuity boundary, and returns the original bytes. Created, Intent, Accepted, old/unknown modes, torn prefixes, missing/corrupt blobs, sequence gaps and budget excess refuse without creating or repairing state. The retained lock remains held. The limits are 4,096 entries and 256 MiB aggregate referenced bytes; partial history is never accepted.

The reader does not execute source or decode financial state. A seven-byte TLMASA1 prefix alone is not canonical action admission. The downstream source reexecutor must use the actual typed action codec and compare all computed observations. The reader currently admits HISTORY-WAL; it deliberately does not assert ESCROW-WAL recovery/supersession closure. That wider cold domain remains open.

SourceIndexHistoryPinV1 now encodes and decodes the exact existing ordered scalar frames emitted by the production enhanced WAL history writer. The codec checks fixed fields/order/types/profiles, known namespace, canonical integers/hex, aligned complete metadata/storage/row receipts, limits and byte-for-byte reencoding. A decoded pin is still an integrity expectation: actual file CRC/full KV/row validation remains mandatory. No new wire magic, financial-state decoder or expected-result importer is introduced.

## Validation and remaining gates

Root validation passes 436 library tests (four ignored child entries), 44 public compatibility checks, all-target Clippy with warnings denied, Cargo fmt, 234 included-file formatting checks, route inventory and supply-chain checks. This cycle adds 23 controls: nine escrow/wiring (four metadata plus five actual Core), nine read-only ACK history (seven metadata plus two actual Core), and five pin codec (four metadata plus one actual production-writer comparison). Counts overlap the library suite.

The first build found the newly composed read-only test owner missing the existing cfg(test) process-exit commit-probe initializer. Initializing that optional test probe to None fixed composition without changing production behavior or expected results; the failed build log is preserved. Both actual source Start/Pause and catchup/native Append/Resolve histories cold-open after the financial controller is dropped.

Full acknowledged financial action replay, inline source continuation/recovery, a cross-publication source-history adapter, actual process-loss financial restoration, intended-host power-loss/performance validation and authenticated chain/UTXO/actor evidence remain open. Windows tests use explicit FileSyncOnly; directory durability and power-loss survival are not established. The full all-target release baseline remains 1,977 Rust/238 locked numeric checks; this scoped validation does not promote it. No integrity hash supplies authentication or complete-block fraud-proof coverage.

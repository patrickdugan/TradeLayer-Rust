# Funded periodic epochs in the economic owner

Optional `EconomicConfig.funding` integrates the pure [funding calculations](FUNDING.md) into the complete [economic owner](ECONOMIC.md). `EconomicState` still has one Joint-owned Ledger. Funding reads the owner's actual available collateral, debits every payer into one derived transient epoch escrow, credits receivers from that same escrow, checks zero residue, and commits the epoch with the complete block. No separate funding ledger, margin-map balance, insurance credit, or reusable payment pool is created.

The explicit execution policy is `FundingPolicy::ConservingFundingV1`. The selected oracle, perpetual-contract configuration, prices, actor identities, external transaction IDs, and blocks remain unverified deployment/caller inputs. This is a functional funded driver with declared repairs; it is not a complete clearing implementation or historical consensus promotion.

## Scope and event ordering

Funding is opt-in for one configured oracle-backed contract and collateral property. `oracle_id` must be nonzero. `max_staleness_blocks` is independently configured from zero through 192. The economic fee route must classify the contract as Oracle; the caller still supplies the contract's perpetual identity and notional policy. Native-contract VWAP selection, expiry/final settlement, vaulted synthetic funding, and options are outside this driver.

The owner observes configured-oracle publications and closures only after the original Joint/Registry action is admitted. Existing activation, oracle-admin equality, closed-oracle, input replay, and positive 1e4-quote checks apply. A supplied publication has no independent backdated or future height field: its observation takes the current admitted block height and the resulting Registry quote. Quote prices are converted from the registry's integer 1e4 units.

Ordinary Joint actions and contract orders/cancellations are processed through the economic block's existing phases. Contract matches settle first. Funding then captures nonflat signed contract positions and the owners' actual available collateral. Funding does not draw margin or pay through IOUs. The owner subsequently refreshes position projections and finalizes the Joint/Spot portion. Spot finalization can change available balances after the funding capture; captured funding available balances are therefore an explicitly timed observation, not a second live balance authority.

If any payer lacks the required available atoms, a receiver addition overflows, a transfer fails, a resource bound is exceeded, or final checkpoint validation fails, the entire private block clone is discarded. Earlier ordinary sends, contract fills, fees, oracle updates, replay identities, and funding transfers from that block do not partially publish.

## Cadence, observations, and status

The source `Clearing.applyFundingRates` cadence is block height divisible by 24. This is a block cadence, not a chain-independent promise of one wall-clock hour. An epoch runs only after type 18 has been activated in an earlier block. For activation height A and finalized height F, the required epoch count is:

```text
floor(F / 24) − floor(A / 24), clamped at zero
```

Each expected epoch has its exact scheduled height and a deterministic ID binding the economic domain, network/genesis, contract, collateral, and height. The driver records scheduled epochs even when they have no payment legs. Status distinguishes `ClosedOracle`, `MissingPrice`, `StalePrice`, `ZeroRate`, `NoPositions`, and `Paid`. A nonzero rate whose individually rounded charges total zero can have a valid empty payment plan; `Paid` records the selected plan branch rather than guaranteeing a nonzero amount.

The scoped averaging window is inclusive `[height − 192, height]`, with the lower bound saturated at zero. This follows source `oracle.getTWAP`'s `$gte`/`$lte` bounds; 193 distinct integer heights can be included. The averaging arithmetic is equal observation-row weighting, sum/count at 20 places, q8 HALF_UP, then the source Number return boundary before `source_rate`.

Publication admission is an explicit Registry integration policy. The existing Joint Registry accepts successive same-height publications, so this driver retains its final accepted quote and transaction ID for that height, giving each height one averaging row. The pinned OracleList high-level `publishData` instead skips when its recorded update height is at or beyond the requested height. It marks that height before later work, so the first attempted update occupies the height even if persistence subsequently fails. Its lower-level `saveOracleData` directly upserts the oracle/height database key and can overwrite that row. The owner's last-accepted-per-height rule follows the existing Registry interface without changing its actor rules. It is not a claim of parity with OracleList's high-level duplicate-publication admission.

The current observation set is pruned by the same trailing bound while retaining the latest quote even if it is older. Keeping that quote allows a deterministic `StalePrice` decision instead of silently forgetting a known old index. A future index is invalid. An index older than the independent staleness allowance does not cause a transfer or an external fallback fetch. Missing price/window, stale price, or closed oracle produces no payment plan. Historical epochs retain their own window/index captures rather than asking today's registry or a remote API to reproduce old input data.

`FundingState.closed_at` records the actual admitted closure's transaction ID and height. Historical closure status derives from whether that height is at or before the epoch; closing the oracle later must not retroactively erase earlier paid epochs. A closure must be consistent with Registry closed state and cannot precede retained later publications. It is an accounting capture of an admitted unverified action, not a cryptographic proof of the action's meaning.

## Source arithmetic and conserving execution repair

The pure helper preserves the actual source rate's operation order: `(index − average) / average` at 20 places, basis points rounded to two places, a five-bps deadband/subtraction, division by eight rounded to four places, magnitude cap 12.5bps, and Number return. Source collateral-notional selection is separate from mark PnL notional. Oracle linear funding uses q8(raw notional × index); inverse funding first divides 1/index at 20 places, then multiplies the raw notional and rounds to eight places. Both cross the source Number boundary.

Execution deliberately repairs source payment defects. Positive rates charge longs and credit shorts; negative rates charge shorts and credit longs. Every payer is charged its own positive q8 HALF_UP amount exactly once using exact fractional Decimal contracts. The sum of actual whole-atom debits is the only receiver budget. Receivers obtain integer floors of their exact proportional shares, then remaining atoms follow descending exact Hamilton remainders, with ascending ASCII owner order for ties. Receiver shares therefore sum exactly to payer charges without source sign inversion or independently rounded over-crediting.

Plans reject duplicate owners, missing nonflat counterparties, insufficient available balances, arithmetic/aggregate overflow, invalid inputs, and receiver overflow before any funding credit. All payer debits occur before the first receiver credit. The economic owner separately requires total signed contract positions to net to zero. A funding plan never treats nominal notional or a funding event row as already-funded custody.

The existing pinned source evidence in `FUNDING.md` characterizes negative-rate inversion, receiver rounding creation, partial dependency failures, cadence, missing/stale/future index selection, and swallowed event-write failures. Those observations remain separate from this owner policy. Its deterministic as-of observations, explicit freshness bound, atomic full-block execution, exact fractional weights, funded Hamilton allocation, and records for zero/skip epochs are named driver/settlement repairs rather than implicit historical acceptance rules.

## Replay, custody, and complete persistence

System funding epoch IDs have a dedicated Joint replay category. They are disjoint from external global inputs, registry inputs, contract/spot input identities, ordinary ledger inputs, and internal custody fingerprints. They share the aggregate Joint replay bound but are not misreported as external wire transactions. Even a zero-leg epoch permanently fences economic history from old standalone Joint/Spot snapshots. Custody legs require an epoch/economic event registered in the same in-progress block; a prior block's epoch cannot authorize later transfers.

The transient funding escrow must end at zero. The general economic verifier rejects unexplained `~econ:` balances, so a leftover funded pool cannot be silently retained outside the exact fee/margin/reserve/loss metadata. Available balances and aggregate token supply remain those of the sole Ledger. Payment records state who was charged or paid and how many atoms; they do not grant transfer authority independently.

Funding-enabled complete state uses TLEC v2 and includes its independent funding config, retained observations, optional closure, complete epoch statuses/IDs, captured index/window/positions, and exact plans/payment lists. The nested private Joint payload uses TLJE v2 when system epoch IDs exist; before the first epoch it can still use canonical TLJE v1 within a funding-enabled TLEC v2. Funding-disabled TLEC v1 and epoch-free TLJE v1 retain their established bytes. Versions cannot be relabelled to discard enabled configuration or system history.

Decoders enforce bounded canonical text, row/list bounds, shared funding record limits before expanding untrusted vectors, sorted/disjoint replay sets, exact scheduled epoch identities, strictly increasing observation heights, no future samples, valid 1e4 observations, net position conservation, and exact recomputation of recorded status/plan. A known observation union across current rows and historical windows/indexes requires one consistent tuple per height and transaction ID. Each epoch window must equal every known row in its inclusive range, and current retention must equal the known trailing range plus the latest quote. Closure IDs are disjoint from every historical observation reference and cannot precede any known publication. At an epoch exactly at the finalized tip, captured nonflat owner/contracts must equal current nonflat owner/contracts; captured available balances retain their earlier timing boundary. The complete owner also verifies actual economic escrows and canonical byte-for-byte reencoding. Rechecksummed malformed metadata is not accepted merely because its CRC is valid. Independent expected network/genesis, economic/funding policy, administrator, permitted spot properties, exact chain tip, and durable head still come from outside the bytes.

The existing `EconomicChain`/`DurableEconomicChain` wrappers retain complete TLEC v2 before-states for rollback and commit the full checkpoint with the sole ledger in one synced Journal frame. Restart, rollback, and reapply restore oracle captures, closures, epoch identities and payments together with the rest of the economic state. The durable head covers those bytes and remains storage-health gated after uncertain I/O. CRC, canonical encoding, hashes and internal history linkage provide local integrity/freshness, not authenticated chain provenance.

## Bounds and remaining gates

The driver permits at most 4,096 retained observations, 4,096 epochs, 4,096 captured positions per epoch, and a shared 65,536 record budget across retained observations and all repeated epoch windows, positions, debits and credits. Index/epoch headers are separately bounded by the epoch count. These limits compose with economic leg/replay limits, bounded rollback depth, the 64 MiB complete checkpoint cap and finite Journal log budget. Even empty/no-payment epochs consume history; the owner does not promise indefinite operation without an explicit retention/migration design. High-density windows or many positions can exhaust the shared record budget before the epoch-count limit. Exhaustion rejects the full staged block rather than pruning audit history silently.

Recomputation establishes consistency with recorded observations and captured positions. It cannot independently prove that every historical publication was included, that a processed ID represented the claimed action, or that every historical position/available snapshot reflects authenticated prior execution. Overlapping retained records and at-tip contract snapshots are checked for consistency; changing all historical evidence consistently still requires an authenticated checkpoint/replay trust boundary. Full historical publication and funding provenance must not be inferred from a registry processed-ID membership test alone.

Remaining promotion gates include authenticated oracle administration and publications, actual chain/UTXO/script validation, independently proven perpetual/expiry configuration, historical bootstrap and replay evidence, complete publication-history provenance, configured stale/closed handling review, default/liquidation/insurance integration, native VWAP funding, bounded archival/retention design, and measured end-to-end resource costs. No new external opcode, mark authorization, insurance lifecycle, or permission to spend user funds follows from enabling this unverified driver.

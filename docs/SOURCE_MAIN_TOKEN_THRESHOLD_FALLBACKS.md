# Raw20 activation fallback continuations

The ordinary V9 raw20 read continuation passes the original upper corpus. The additional 30-frame source corpus exposes fallback saves that cross further awaits: a failed first threshold factory starts its fallback factory before the next attestation read, but writes afterward. A failed threshold find starts its fallback factory after that attestation/property read, and writes at the following awaited property factory. Both operations must remain separate real storage calls.

The revised helper executes the unchanged `SourceActivation` method on a clone using only replies captured from actual, already executed Core DB operations. When the method requests an operation without a captured reply, that internal attempt stops and its clone is discarded. Its exact next dependency is retained. At the source await boundary Core executes that dependency once, records its actual returned or thrown result, and resumes the same original method over those facts. Once it completes, its actual owner replaces the authoritative activation owner and increments its action count once. No default registry, storage success or Boolean result is reconstructed from fixtures. No original activation code or codec changes are required.

The cloned attempts are internal control flow, not public source calls or extra DB effects. Failed attempts do not commit metadata. Pending diagnostics bind the arguments, exact requested dependency, actual prior dependency replies, trace and next boundary. Limits are two source callsites and eight dependency replies per call. Main's public endpoint must drain all jobs. V1–V8 retain their existing paths and bytes.

## Shared owner visibility audit

This is restricted to the exact V9 Main/raw20 source-registry route. The original decoder always produces a Boolean offerer flag. Awaited activation checks and `getAdmin` precede the two un-awaited thresholds. After they start, the only further activation operation is the second threshold, which starts its own DB load without inspecting the current registry. Both threshold return Promises are tested for truthiness rather than their eventual values. Country, property and Tally operations use plain data-only records and do not read the activation registry. Their sufficiency Promises force the original validity refusal, so financial Logic and valid-transaction postphases do not observe an intermediate activation cache. No input callback or arbitrary code executes in this graph.

Each attempt starts from the current authoritative owner, retaining unrelated metadata and completed action counts. Actual source ordering writes fallback A before threshold B's corresponding DB read in the exercised failure paths; B therefore consumes the real current DB state. Source fallback cache assignments can occur earlier than the helper's final physical commit, but the admitted graph has no registry reader at those intermediate points, and the ignored threshold Boolean cannot affect state. The tests compare the full final shared activation state, real fallback write arguments/results and every ordered effect. This is not a general asynchronous Activation API, a claim about arbitrary callbacks or a V9 intermediate-state witness API. Existing TLSW3 still rejects V9.

Four isolated Rust 1.90 actual-owner/helper tests pass, including the explicit find/read/fallback-factory/property-factory/update separation. The actual-source 30-frame/20-call failure fixture is independent and remains the required fresh Cargo gate. Root owns that run, compatibility gates and commit. The replacement helper and single DB-read hook are a separate delta from the earlier ordinary helper; Root transfer and withdrawal continuations are preserved.

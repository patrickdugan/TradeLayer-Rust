# Bitcoin payment/channel input satisfaction

Root integration: four actual-crate integration tests and the private legacy
normalization test pass. The block-bound composition separately passes four
Root tests. Full release promotion is pending; the earlier isolated evidence
and dependency profile below retain their original scope.

`check_bitcoin_standard_input` adds real selected-input signature satisfaction for six explicit templates: P2PKH, native P2WPKH, legacy P2SH 2-of-2, native P2WSH 2-of-2, P2SH-wrapped P2WPKH and P2SH-wrapped P2WSH 2-of-2. It reuses the existing native SHA256d, HASH160 and public-input secp256k1 verifier. It adds no dependency, unsafe code, build script, mutable financial owner or trusted adapter. The existing frozen two-of-two API is unchanged.

Complete funding and spending transaction bytes are parsed through the existing bounded canonical reader. The selected input must reference the actual funding TXID and output index; amount/program/redeem/witness-script/key data are read from those exact bytes. The private receipt borrows both transactions and exposes actual serialized keys, template, amount and each signature's hash mode/digest. There is no caller-supplied amount, signer identity, scriptCode or signature verdict.

All six defined ECDSA modes are supported: ALL, NONE, SINGLE, and each with ANYONECANPAY. Multisig signatures may use different modes. Legacy serialization replaces other scriptSigs, handles sequence/output exclusions and preserves the real SINGLE out-of-range `01 00…00` behavior. Legacy signature pushes are removed at opcode boundaries before hashing, including all supplied multisig items; an equal byte pattern inside pushed data is preserved. BIP143 handles mode-specific prevout/sequence/output hashes and commits the actual selected amount. These fixed templates have no executed CODESEPARATOR; opcode-looking bytes inside pushed public keys remain data. Legacy SINGLE's bug and NONE/SINGLE/ANYONECANPAY's reduced commitments are reported faithfully and never become TradeLayer output authority.

Strict DER is decoded into positive scalar bytes and checked by existing native ECDSA. High-S is accepted under the selected consensus flag profile. Compressed and uncompressed SEC1 keys are supported; hybrid encodings explicitly refuse. Two-of-two signatures are checked in actual script-key order. Repeated keys and identical valid signatures are allowed where Bitcoin CHECKMULTISIG permits them; this proves neither distinct participants nor protocol eligibility.

The only accepted flag mask is `0x0e15`, Core's pre-Taproot P2SH/DERSIG/NULLDUMMY/CLTV/CSV/WITNESS profile. It is a declared verification profile, not proof of active-chain deployment. It does not establish node relay standardness: LOW_S and witness compressed-key policy are absent. Native scriptSigs must be empty; wrapped programs require exactly the canonical single program push. Legacy unlocking is push-only and exactly the required stack shape; nonminimal legacy data pushes remain accepted under this mask. Arbitrary Script, other multisig templates, extra legacy stack elements/opcodes, future witness versions, other hash/flag bits, hybrid keys and unsupported transaction domains refuse. Existing nonempty input/output and size/count limits remain in force.

## Authentication remains separate

The receipt permanently refuses authenticated funding inclusion/unspentness, complete transaction/chain consensus and TradeLayer actor/economic admission. It does not validate other inputs, value conservation/fees, finality, funding validity/maturity, block inclusion, current UTXO membership or chain/rule context. The existence of matching raw funding bytes is not unspentness. Hash modes can deliberately leave outputs or other inputs unsigned. A full adapter must independently bind the actual chain/UTXO facts, whole transaction and exact protocol operation/actor policy; weak signatures are not permission for unsigned TradeLayer state changes.

No follower, economic gate, default policy, old API or checkpoint format changes. Litecoin MWEB, Dogecoin AuxPoW and chain-specific admission are not enabled. Root should add the module declaration and copy the four additive payload files, then run its actual current crate checks before committing. Isolated checks used immutable corrected provider `a19118368cf9ccd4ee6e14b36df0f775b4cc0c6ba345eafa9bfcb5f3ecc55c7a`; no whole-Core build or Root edit was performed by this stage.

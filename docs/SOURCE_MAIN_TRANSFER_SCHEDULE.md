# V9 Main transfer read scheduling

The first fresh upper Main differential failed at `upper/proof-06-indexed-type-22`: effect 5 was a Rust `db` read where the unchanged source issued a second `database` factory. This is a runtime scheduling defect, not an observer label defect.

Pinned `validity.js` calls `Channels.isValidChannel(sender)` without awaiting it, then immediately awaits `Channels.getChannel(sender)`. Both methods see the initially missing shared cache. With the source's asynchronous DB factory, the observable order is factory 1, factory 2, find 1, find 2. Completing the first method eagerly changes that order and suppresses a real second read when the first load finds the channel.

The correction is restricted to exact `SpotLifecycleV9`, an active Main call and raw type 22. A local Types backend captures actual factory/read results, then resumes the original SourceChannels load body twice against its one registry. It does not manufacture channel data or a financial result. Both lookups begin before either load commits; both reads execute before either cache assignment. Original arguments, argument validation, state validation and one action per owner call are retained. A first successful load survives a second load's rejection.

The local backend drains before Types returns, including a rejected Types result. No continuation or receiver is retained at a public command boundary. A source un-awaited rejection is recorded in the existing replay-bound `source_unhandled_rejections`; exact V9 Main emits its rejection notification after awaited Main work. No new checkpoint field or codec is needed. V1–V8 call paths, admissions and diagnostic bytes are unchanged.

`main_transfer_schedule_vectors.cjs` runs the unchanged pinned Main, Types, Validity and Channels business bodies. It adds explicit one-shot factory fault input to the existing data-only DB adapter, with the same skip/message behavior as existing find/update faults. The adapter records failures rather than supplying validation or settlement answers. The ordinary document-backed TxUtils profile and actual persisted Activation registry are retained.

The new corpus has 30 frames: 10 constructor/input resets and 20 actual Main calls, with no unavailable exclusions. It covers empty and funded caches, first/second factory failures, first/second find failures in indexed and live Main, and processed retries. Full state and effects retain actual registries, tables, books, positions, synthetic/proof inputs and notification order. Both genuine BigNumber 9.3.1 and 9.1.2 reproduce fixture SHA-256 `3751f92a764eab38f7cb76c4a3d6535048d9ca3538fc28080c49737292eeeb69`.

Work-stage validation: Rust 1.90 formatting, test metadata and test Clippy pass. Four isolated Rust tests compile the revised actual SourceChannels owner plus the exact continuation helper over a small DB test adapter; they pass for normal/funded loads, cached reads, both factory failures and both find failures. The isolated harness links the immutable cached library SHA-256 `6b67896d09dc9cbe48cf4fb67e1349813661f8b6633705b476774ebb77d8e3ac` only for unchanged public value/decimal dependencies. It is not a full runtime build. Root owns the fresh Cargo differential, compatibility gates and commit.
